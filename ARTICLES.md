# The article standard

What an article on trevorju.dev is made of, where each file lives, and how the
text is shaped. Any session writing or reviewing an article follows this file.

## An article is not the README

A README tells someone how to install and use the repo. An article tells the
story: what the project is, why it exists, what it achieved, how it works. They
are different documents with different readers, so they are different files.

## The files

```
<project repo>/
├── README.md              for people using the repo. The site does not touch it.
└── article/
    ├── article.md         the article. Plain Markdown. The only file you write.
    └── *.png *.svg *.gif  its visuals, if any, referenced as ./name.png
                           a video is ![what it shows](./name.mp4): the page plays it
                           silently on a loop; keep it short and a few MB at most
                           a YouTube link alone on a line, written <https://www.youtube.com/watch?v=ID&t=287s&end=297>,
                           becomes a player that starts (and, with end, stops) at those seconds
    └── demo/index.html    optional: a live demo, shown at the top of the page

trevorju.dev/              (written by /sync, never by hand)
├── projects/<name>        the pin: the commit the page is built from
└── notes/<name>/
    ├── notes.md           what an agent needs to know about the project
    └── log.md             one line per sync

trevorju.dev, the site     (generated by build.py, never edited)
├── /<name>/               the page
├── /<name>.md             the page as markdown: article.md, then notes.md
└── /llms.txt, /llms-full.txt, the home page row
```

So writing an article means creating one Markdown file, and any images it
needs, in the project repo and committing them there. Everything else follows
from `/sync` and `/publish`.

A project with no `article/article.md` still gets a page: the site falls back
to `README.md` and `/check` says so.

## The format

GitHub-flavoured Markdown. No front matter, no HTML, no custom syntax. The
title, one-liner, date, commit and reading time on the page are all taken from
the file and from git; nothing is typed twice.

## The fixed rule: how it opens

```markdown
# Agent-native site

A portfolio that any agent session can post to.

Every project page is built from that project's own GitHub repo at a pinned commit. The session that did the work writes it up and adds it from wherever it is working, so nobody has to open the portfolio to update the portfolio.

## Why
...
```

Three lines, in this order:

1. **The title.** The `# ` line is the project's name and nothing else. It does
   not change.
2. **One sentence.** Alone in its own paragraph: what the project is, said as
   plainly or as memorably as it can be. It is also the line under the title
   on the home page.
3. **An abstract.** The next paragraph, a sentence or two: what it does and why
   it matters.

Each has to make sense with nothing around it, since together they are the
first three lines an LLM is handed.

On the page the sentence and the abstract run together as one paragraph.

The page then shows the repo and the last-updated date on one row under the
abstract. Both come from git; do not write them in the file.

The home page opens the same way: the name, one sentence, an abstract. Those
two lines are `tagline` and `abstract` in `site.toml`.

After that, use `##` sections. Each one becomes a dash in the page's section
indicator, so keep their names short. Which sections to use is up to the
project.

## Visuals: where they earn their place

Trevor likes visuals in an article, used appropriately. That means:

- Use one where a picture explains something the text cannot do as well: how
  the parts connect, what the thing looks like running, the shape of a result.
- Put it where the reader needs it, next to the text it explains. It does not
  have to be at the top.
- Do not add one to fill a slot. An article with no visual is fine. A diagram
  that restates the paragraph beside it, or a list of facts dressed up as a
  graphic, is worse than none.
- Keep the files in `article/` beside the text and link them relatively.
- Every image has alt text that says what it shows. The markdown twin and an
  LLM reader get the alt text and not the picture.
- Check it at phone width. Text inside an image shrinks with it.

## A live demo

A project can ship one demo: `article/demo/index.html`, a complete page of its
own with whatever files it needs beside it. The site copies the folder to
`/<name>/demo/` and shows it in a frame at the top of the article, under the
repo row. The article file itself stays plain Markdown.

- It must work when opened on its own, at phone width, with no build step.
- It may link `/assets/tokens.css` to pick up the site's colours and fonts, with
  fallbacks for when that file is not there.
- The frame is sized to the demo. The demo reports its height with
  `parent.postMessage({type: "demo-height", height: <px>}, "*")` whenever it
  changes.
- It hosts nothing it has no right to host. A demo that plays someone else's
  music or video embeds the owner's own player.
- Use one where trying the thing shows more than reading about it. Most
  projects do not need one.

## Numbers

If the project has measured results, say them plainly and early enough that a
skimming reader meets them, with what each one measures and against what.
There is no required list and no required count. If nothing has been measured,
say nothing. Never invent or estimate a number.

## What `/check` looks for

| Rule | Check | Result |
|---|---|---|
| The file exists | `article/article.md` is present | warn, and README is used |
| Title | first line starts with `# ` | error |
| One sentence | the first paragraph is prose, not a list, heading or image | warn |
| Abstract | a second prose paragraph follows it | warn |
| Alt text | every image has some | warn |
| Demo | `article/demo/` holds no symlinks | error |

Nothing checks for a visual or a number being present. Whether an article
needs one is a judgement, not a rule.

## History

- 2026-11-13: the first version required a numbers list and a visual before
  the first section. Trevor found that too strict after seeing it applied:
  keep the opening sentence, keep visuals, but use them where they fit.
- 2026-11-13: the opening became three lines, title, one sentence, abstract,
  after the layout of articles on claude.dev. The title stays the project name.

- 2026-11-13: a project may ship a live demo, after bar2vec's section names
  turned out to be easier to judge by listening than by reading scores.
