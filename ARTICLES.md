# The article standard

What an article on trevorju.dev is made of, where each file lives, and how the
text is shaped. Any session writing or reviewing an article follows this file
and nothing else.

## An article is not the README

A README tells someone how to install and use the repo. An article tells the
story: what the project is, why it exists, what it achieved, how it works. They
are different documents with different readers, so they are different files.

## The files

```
<project repo>/
├── README.md              for people using the repo. The site does not touch it.
└── article/
    ├── article.md         the article. Plain Markdown. The only file you write.
    └── *.png *.svg *.gif  its visuals, referenced as ./name.png

trevorju.dev/              (written by /sync, never by hand)
├── projects/<name>        the pin: the commit the page is built from
└── notes/<name>/
    ├── notes.md           what an agent needs to know about the project
    └── log.md             one line per sync

trevorju.dev, the site     (generated by build.py, never edited)
├── /<name>/               the page
├── /<name>.md             the page as markdown: article.md, then notes.md
└── /llms.txt, /llms-full.txt, the home page row
```

So writing an article means creating one Markdown file and its images in the
project repo, and committing them there. Everything else follows from `/sync`
and `/publish`.

A project with no `article/article.md` still gets a page: the site falls back
to `README.md` and `/check` says so.

## The format

GitHub-flavoured Markdown. No front matter, no HTML, no custom syntax. The
title, one-liner, date, commit and reading time on the page are all taken from
the file and from git; nothing is typed twice.

## The shape

Everything above the first `##` heading is the opening, and its order is fixed:

```markdown
# Project name

One standalone sentence: what it is and why it matters.

- **84%** pass rate on 120 held-out cases, up from 61%
- **3×** cheaper per run than the first version

![What the diagram or screenshot shows, in words](./overview.png)

## Why
...
```

1. **Title.** `# ` and the project's name.
2. **One standalone sentence.** Alone in its own paragraph. It has to make
   sense with nothing around it: it is also the one-liner on the home page and
   the first line an LLM is handed.
3. **The key numbers.** A short list, each item starting with the number in
   bold, then what it measures and against what. Two to four items. If nothing
   has been measured yet, leave the list out. Never invent or estimate a number.
4. **The first visual.** A diagram of how it works, a screenshot or clip of it
   running, or a chart of the result. Not decoration.

After the opening, use `##` sections. Each one becomes a dash in the page's
section indicator, so keep their names short. Which sections to use is up to
the project; "Why", "How it works", "Results" and "What I'd change" are a
reasonable default.

## Visuals

- Keep them in `article/` beside the text and link them relatively.
- Every image has alt text that says what it shows. The markdown twin and an
  LLM reader get the alt text and not the picture.
- Prefer a real screenshot or a diagram of the mechanism over an illustration.

## What `/check` looks for

| Rule | Check | Result |
|---|---|---|
| The file exists | `article/article.md` is present | warn, and README is used |
| Title | first line starts with `# ` | error |
| One standalone sentence | the first paragraph is prose, not a list, heading or image | warn |
| Numbers early | a figure appears before the first `##` | warn |
| Visuals | at least one image, each with alt text | warn |

Warnings never block a publish. A project with nothing measured yet has no
number to show, and a made-up one is worse than none.
