# The article standard

What an article on trevorju.dev is made of, where each file lives, and how the
text is shaped. Any session writing or reviewing an article follows this file.

## An article is not the README

A README tells someone how to install and use the repo. An article tells the
story: what the project is, why it exists, what it achieved, how it works. They
are different documents with different readers, so they are different files.

## The files

```
<project repo>/
├── README.md              for people using the repo. The site does not touch it.
└── article/
    ├── article.md         the article. Plain Markdown. The only file you write.
    └── *.png *.svg *.gif  its visuals, if any, referenced as ./name.png

trevorju.dev/              (written by /sync, never by hand)
├── projects/<name>        the pin: the commit the page is built from
└── notes/<name>/
    ├── notes.md           what an agent needs to know about the project
    └── log.md             one line per sync

trevorju.dev, the site     (generated by build.py, never edited)
├── /<name>/               the page
├── /<name>.md             the page as markdown: article.md, then notes.md
└── /llms.txt, /llms-full.txt, the home page row
```

So writing an article means creating one Markdown file, and any images it
needs, in the project repo and committing them there. Everything else follows
from `/sync` and `/publish`.

A project with no `article/article.md` still gets a page: the site falls back
to `README.md` and `/check` says so.

## The format

GitHub-flavoured Markdown. No front matter, no HTML, no custom syntax. The
title, one-liner, date, commit and reading time on the page are all taken from
the file and from git; nothing is typed twice.

## The one fixed rule: how it opens

```markdown
# Project name

One standalone sentence: what it is and why it matters.

## Why
...
```

A title, then **one standalone sentence**, alone in its own paragraph. It has
to make sense with nothing around it: it is also the one-liner on the home page
and the first line an LLM is handed.

After that, use `##` sections. Each one becomes a dash in the page's section
indicator, so keep their names short. Which sections to use is up to the
project.

## Visuals: where they earn their place

Trevor likes visuals in an article, used appropriately. That means:

- Use one where a picture explains something the text cannot do as well: how
  the parts connect, what the thing looks like running, the shape of a result.
- Put it where the reader needs it, next to the text it explains. It does not
  have to be at the top.
- Do not add one to fill a slot. An article with no visual is fine. A diagram
  that restates the paragraph beside it, or a list of facts dressed up as a
  graphic, is worse than none.
- Keep the files in `article/` beside the text and link them relatively.
- Every image has alt text that says what it shows. The markdown twin and an
  LLM reader get the alt text and not the picture.
- Check it at phone width. Text inside an image shrinks with it.

## Numbers

If the project has measured results, say them plainly and early enough that a
skimming reader meets them, with what each one measures and against what.
There is no required list and no required count. If nothing has been measured,
say nothing. Never invent or estimate a number.

## What `/check` looks for

| Rule | Check | Result |
|---|---|---|
| The file exists | `article/article.md` is present | warn, and README is used |
| Title | first line starts with `# ` | error |
| One standalone sentence | the first paragraph is prose, not a list, heading or image | warn |
| Alt text | every image has some | warn |

Nothing checks for a visual or a number being present. Whether an article
needs one is a judgement, not a rule.
